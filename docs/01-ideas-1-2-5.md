## Idea 1 — Support escalations over phone

### The problem (specific)

AI support and ticket queues fail in two expensive ways:

1. **Silent failure** — bot or agent “resolves” or loops; customer gives up.  
2. **Wrong altitude** — issue needs a human voice (enterprise, seething customer, ambiguous outage) but the system only offers more chat.

Phone is still how high-trust recovery happens. Nobody wants an unsupervised agent freelancing cold calls without structure, consent, or writeback.

### Who hurts

- Support / CS managers (SLA, CSAT, churn)  
- On-call / TAM for strategic accounts  
- Customers waiting for a real answer  

### Product sketch

**Name working title:** `support-phone-escalation` (skill) + thin console (optional app)

| Step | Behavior |
| --- | --- |
| Trigger | Ticket tag `phone-escalation`, SLA risk, “customer requested callback”, or Sev path |
| Authorize | Human or policy allowed this number + purpose; dry-run shows script intent |
| Call (CALL-E) | Outbound to **customer** *or* **internal owner** (config) |
| Goal of call | Confirm impact, gather missing facts, set expectation, book next step |
| Result schema | `outcome`, `severity_ok`, `facts[]`, `next_action`, `callback_window`, `sentiment_self_report` (optional, not inferred) |
| Writeback | Ticket note + optional Slack |

### CALL-E usage depth

- `plan_call` with constrained script / disclosure budget  
- `run_call` live  
- `get_call_run` → map to schema  
- Retry / status polling  

### Why it can win Practical

Judges hear “I would use this Monday.” Authentic domain. Not a sales spam bot.

### Risks

- Consent / TCPA-ish norms — always “we’re calling about your open case …”  
- Demo needs a safe real/test number workflow  
- Looks like “generic support AI” if UI is vague — **name the trigger and writeback**  

### MVP cut

One trigger source (even CSV / manual form), one call direction (customer **or** internal — pick one for demo), structured JSON + markdown ticket comment, dry-run.

## Idea 2 — Enterprise account health callback

### The problem (specific)

Strategic accounts decay in silence: usage drop, support spike, champion leaves, renewal in 60 days. CS plays “QBRs and hope.” Phone outreach from a human doesn’t scale; email is ignored; chatbots don’t carry executive weight.

A **targeted, consented, high-context** phone touch — not a blast — can re-open the relationship with structure.

### Who hurts

- CS / account managers  
- Revenue leaders (renewal risk)  
- Customers who are stuck but not complaining in-ticket  

### Product sketch

**Name working title:** `account-health-callback`

| Step | Behavior |
| --- | --- |
| Trigger | Health score drop, unused seats, open escalations count, “at-risk” flag (input can be fake CRM JSON for hackathon) |
| Authorize | AM approves “call this contact about X” in UI (human-in-loop for v1) |
| Call | To named champion / economic buyer contact on file |
| Goal | Confirm status, surface blockers, offer help path, schedule follow-up |
| Result | `account_status`, `blockers[]`, `asks[]`, `meeting_requested`, `urgency` |
| Writeback | CRM note / Notion / Slack “at-risk” channel |

### Why it’s strong

- Clear buyer (CS leader)  
- Phone is appropriate for high-value accounts  
- Differentiates from Idea 1 (proactive relationship vs reactive ticket)  

### Why it’s weaker for a 6-week hack than Idea 1

- Needs believable “health signal” story; fake CRM is fine if honest  
- Risk of looking like **sales dialer** if framing is “book a meeting” first  
- Less “urgent demo theater” than a Sev escalation  

### Positioning fix

Frame as **customer success recovery**, not outbound SDR. Script: “checking in on your open adoption blockers,” not “renewal is coming.”

### MVP cut

JSON account object → AM clicks **Approve call** → CALL-E → result card → Slack webhook. One persona, one contact.

## Idea 5 — Incident bridge: call human when agent is stuck

### The problem (specific)

Agent systems (OpenClaw, support bots, coding agents) hit walls: tool failure, policy boundary, ambiguous user intent, production risk. Today they either:

- hallucinate past the wall, or  
- dump a text notification that gets buried  

**Phone is a high-priority interrupt** for the right human: “I cannot complete step X; need a decision in 2 minutes.”

### Who hurts

- People running always-on agents  
- On-call / eng managers  
- Anyone who has been burned by silent agent failure  

### Product sketch

**Name working title:** `agent-stuck-phone-bridge`

| Step | Behavior |
| --- | --- |
| Trigger | Agent emits `needs_human` with reason + context pack (redacted) |
| Authorize | Allowlist of phone numbers; severity threshold |
| Call | To on-call / owner |
| Goal | Get a **spoken decision** or approval code / choice among options |
| Result | `decision`, `option_id`, `verbatim_summary`, `caller_confirmed` |
| Writeback | Resume agent run / open ticket / post to incident channel |

### Why it can win Practical *and* touch Innovative

- Novel **channel role**: phone as agent control plane, not customer spam  
- Maps to existing CALL-E examples (approval gates) but **your** twist is agent-runtime integration story  
- OpenClaw / multi-agent world is timely  

### Risks

- Looks like a thin wrapper on `deployment-approval-call` if you don’t own a distinctive trigger  
- Must be **not** “call 911” or medical/emergency  
- Demo must show agent stuck → call → agent continues  

### MVP cut

Fake agent state machine with a “stuck” button → CALL-E call with 2–3 spoken options → agent proceeds on structured result. Optional: OpenClaw skill that emits the trigger.

## Unification option (recommended discussion)

**Do not ship three products.** Consider one **brand** with one primary path:

### Option A — **Phone Ops for customer-facing teams** (1 primary, 2 secondary)

Core: support escalation.  
“Same engine, different trigger pack” = account health as a second skill config later (maybe not in demo).

### Option B — **When systems need a human voice** (1 + 5)

Core: escalation **either** to customer **or** to internal owner when automation is stuck.  
One product story: *last-mile human over the phone.*  
Demo path 1: customer callback on ticket.  
Demo path 2 (30 sec): agent stuck → call on-call.  

### Option C — Pure **5** as innovative + practical

If you want the OpenClaw / agent-runtime narrative front and center.

### Option D — Pure **2**

Only if you want CS/revenue narrative and accept softer demo urgency.

**Provisional recommendation:** **Option B (1+5 unified)** — one CALL-E pipeline, two triggers, one writeback contract. Maximizes Assaf authenticity + demo contrast + still Practical-first.
